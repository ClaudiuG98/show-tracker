I want you to create a detailed implementation plan for a Chrome/Edge browser extension that acts as a local TV episode tracker integrated with IMDb.

IMPORTANT: Do not implement the extension yet. First inspect the repository and the supplied sample files, then produce a detailed technical plan for my approval.

Working description
===================

The extension should let users import their IMDb TV-show list and optionally their TV Time export, track watched episodes locally, see the next episode they need to watch for each show, and see future episodes in an Upcoming tab.

This is not a TV Time clone. It should only reproduce the useful episode-tracking workflow.

There should be:

- No community features
- No comments or reactions
- No user accounts
- No cloud backend
- No central application database
- No social features
- No movie tracking in the MVP
- No requirement to log in through the extension

All user information should remain in the browser.

Technology and architecture
===========================

Plan a Manifest V3 extension written in TypeScript.

Recommend and justify an appropriate UI/build stack. Prefer a maintainable but lightweight architecture. Consider React with Vite, WXT, or a similarly appropriate setup, but do not introduce unnecessary complexity.

The initial browser targets are:

- Google Chrome
- Microsoft Edge

Structure the code so Firefox support could be considered later, but do not let Firefox compatibility delay the MVP.

Use a provider abstraction for television metadata so TVMaze can initially be used without permanently coupling every part of the application to it.

For example, the plan should define an interface conceptually similar to:

interface TelevisionProvider {
  lookupByImdbId(imdbId: string): Promise<ProviderShow | null>;
  lookupByTvdbId(tvdbId: number): Promise<ProviderShow | null>;
  getEpisodes(showId: number): Promise<ProviderEpisode[]>;
  getChangedShows(since: SyncWindow): Promise<Map<number, number>>;
}

TVMaze should be the first provider.

Use the following TVMaze functionality:

- Exact show lookup using an IMDb ID
- Exact show lookup using a TVDB ID
- Complete regular episode list for a show
- Show status, such as Running or Ended
- Episode airdate
- Episode airtime
- Episode airstamp when available
- Show update timestamps
- Show images when available

Relevant endpoint patterns include:

- /lookup/shows?imdb=:imdbId
- /lookup/shows?thetvdb=:tvdbId
- /shows/:id
- /shows/:id/episodes
- /updates/shows?since=day
- /updates/shows?since=week
- /updates/shows?since=month

Do not fetch TVMaze's complete future schedule for routine operation if the locally tracked episode lists are sufficient.

Respect TVMaze attribution, licensing, caching and rate limits. Include graceful HTTP 404 and HTTP 429 handling, bounded retries, exponential or appropriate backoff, and request concurrency limits.

Local storage
=============

There should be no server database.

Plan to use:

1. chrome.storage.local for important user-owned state:
   - Tracked-show records
   - Provider ID mappings
   - Watched episode state
   - Paused/not-started state
   - Import decisions
   - Settings
   - Watched-action history
   - Last synchronization information

2. IndexedDB for replaceable or larger cached data:
   - Complete TVMaze episode lists
   - Show and season metadata
   - API response cache
   - Optional image cache

Keep user progress separate from API metadata so cached metadata can be discarded and rebuilt without losing progress.

Include:

- Export local tracker backup to JSON
- Restore local tracker backup from JSON
- Schema versioning
- Storage migrations
- Safe recovery from partial or interrupted imports
- An option to reset cached metadata without resetting watch progress

Do not rely on chrome.storage.sync for the complete tracker.

Canonical identifiers and matching
==================================

Use TVMaze show ID as the canonical provider ID after successful mapping.

Preserve all available external IDs:

- IMDb title ID
- TVDB show ID
- TVMaze show ID
- TVDB episode ID when available
- TVMaze episode ID

Matching priority:

1. IMDb ID from the IMDb CSV -> exact TVMaze IMDb lookup
2. TVDB show ID from TV Time -> exact TVMaze TVDB lookup
3. If both resolve to the same TVMaze ID, merge automatically
4. If they resolve differently, flag a conflict
5. Only use title/year matching as a controlled fallback
6. Never silently accept an ambiguous title match
7. Present uncertain matches for user confirmation

Account for:

- Alternate show names
- Country-specific titles
- Remakes with the same name
- Anthology shows
- TV Time grouping that may differ from TVMaze
- Season numbering differences
- Renamed shows
- Missing IDs
- Deleted or merged provider records

TV Time ZIP importer
====================

Inspect the real ZIP and determine its internal file structure and JSON schema.

Extract, where available:

- TVDB show IDs
- TVDB episode IDs
- Show names
- Season numbers
- Episode numbers
- Episode names
- Watched flags
- Watched timestamps
- Rewatch counts
- TV Time show status
- Date added
- Stopped or paused state
- Any useful metadata for matching

TV Time watched history has priority over assumptions made from the IMDb list.

The importer must not assume that every episode marked unwatched in the TV Time export is already available. Future episodes may exist in exports.

An episode should enter the current backlog only when:

- It is not marked watched
- It is a regular episode
- Its release date/time indicates that it has aired or become available

Map TV Time progress to TVMaze using this priority:

1. Exact TVDB episode ID when TVMaze exposes a compatible external mapping
2. TVMaze show ID plus season and episode number
3. Controlled title/date fallback only when necessary
4. Manual review for unresolved mappings

Treat stopped shows as Paused by default.

Do not let specials create thousands of false backlog entries.

For the MVP:

- Use regular episodes for primary progress
- Ignore insignificant specials in Watch List calculations
- Preserve mapped watched specials if practical
- Put unresolved significant specials into an optional review report
- Explain in the plan how significant specials could be supported later

Combined-import behavior
========================

When both files are supplied:

- IMDb determines membership in the imported IMDb collection and supplies IMDb addition dates
- TV Time supplies watched progress where available
- TVMaze supplies current show status, episode metadata and release scheduling
- TV Time-only shows should be shown in the import report
- Let the user decide whether TV Time-only shows should also be added to the tracker
- IMDb-only shows must go through the appropriate assumption/review flow

Do not ask the user to review shows whose progress was confidently established through TV Time unless there is a conflict.

IMDb-only onboarding
====================

Do not include a "Plan to watch" bulk-question option.

For finished IMDb-only shows, ask:

"What does this IMDb list contain?"

Options:

1. "I have watched everything in this list"
2. "This list is a mixture"

Finished means the TVMaze show is Ended and there are no relevant future regular episodes.

If the user chooses "I have watched everything in this list":

- Mark all regular episodes that were available before the import moment as watched
- Do not mark future episodes watched
- Be careful with episodes released on the current date when no exact time exists

If the user chooses "This list is a mixture":

- Display the relevant shows sorted by IMDb Created date descending
- Assume each show is watched/caught up unless the user selects it as not watched
- Use copy such as: "Select the shows you have not watched yet"
- Selected shows become Not started
- Unselected shows have all currently available regular episodes marked watched
- Allow individual progress adjustment before completing the import

Active or incomplete IMDb-only shows
====================================

Shows that are not fully finished must always be presented for progress review.

This includes shows where:

- TVMaze status is not Ended, or
- Future regular episodes are known, or
- The data is insufficient to confidently classify the show as completely finished

For these shows:

- Default conservatively to current aired episodes being unwatched
- Let the user select the episodes already watched
- Provide fast actions so onboarding is not tedious:
  - Caught up
  - Not started
  - Choose last watched episode
  - Select episodes manually

"Choose last watched episode" should mark all previous regular episodes through that episode as watched.

The episode-level interface must still permit gaps, because some users may skip episodes.

When TV Time already provides progress for an active show, prefill it and do not reset it to unwatched.

WATCH LIST behavior
===================

The Watch List should display only one card per show.

For each eligible show:

1. Find all regular episodes that are already available
2. Exclude watched episodes
3. Sort them in normal airing order
4. Display only the earliest aired unwatched episode
5. Show the number of additional aired unwatched episodes

Example:

SILO
S03 | E03  +4
Episode title
[watched checkmark]

The "+4" count means four additional aired and unwatched episodes. It must not include future episodes.

When the user presses the watched checkmark:

1. Mark the displayed episode watched locally
2. Record a watched-history action
3. Immediately advance the card to the next aired unwatched episode
4. If no aired unwatched episode remains, remove the show from Watch List
5. If the show has a future scheduled episode, it remains in Upcoming
6. Do not require an API request for this local transition

The default show-card ordering should prioritize recent activity. Propose and document a precise sorting rule.

A reasonable default is:

- Sort shows by their most recently released currently-unwatched episode, newest first
- Within a show, always display the earliest unwatched aired episode

Consider optional alternative sorting later:

- Oldest backlog first
- Alphabetical
- Manually pinned

A show with state Not started or Paused should not flood Watch List by default.

Moving from Upcoming to Watch List
==================================

When TVMaze provides an exact airstamp:

- Store it
- Display it in the user's timezone
- Schedule a browser alarm where appropriate
- When the timestamp passes, recompute availability locally
- Move the episode from Upcoming to Watch List without waiting for another TVMaze request

Browser alarms are not guaranteed to run while a browser is completely closed, so also recompute all availability:

- At extension startup
- When the dashboard opens
- When the browser resumes
- After metadata synchronization

When only an airdate is known:

- Treat it as a date-only release
- Provide a configurable local release hour
- Propose a sensible default, such as 09:00 local time
- Clearly represent this as an extension preference, not a guaranteed service release time
- Optionally show "Releases today" before the configured hour

Do not repeatedly poll TVMaze around the release time.

The local stored release time should determine the Watch List transition.

A later refresh can discover:

- Schedule corrections
- Episode title changes
- Newly announced following episodes

Refresh and synchronization
===========================

Do not refetch every tracked show on every extension opening.

Use TVMaze show updates:

1. Store the last known update timestamp for every tracked TVMaze show
2. Periodically request changed-show timestamps
3. Intersect the response with locally tracked TVMaze IDs
4. Fetch show/episode data only for locally tracked shows whose update timestamp changed
5. Update the local metadata cache
6. Recalculate Watch List and Upcoming

Propose a synchronization schedule that balances freshness and API use.

Possible behavior:

- Once daily as the reliable baseline
- Optionally every few hours while the browser is active
- On manual refresh
- On initial import

For long gaps:

- since=day for short gaps
- since=week for longer gaps
- since=month when appropriate
- full update timestamp list only when necessary

Ended shows:

- Do not poll every ended show individually
- Refresh ended shows when TVMaze reports their update timestamp changed
- This should catch revivals, specials, corrections or newly added episodes
- Consider an infrequent integrity refresh only as a defensive fallback, and justify it
